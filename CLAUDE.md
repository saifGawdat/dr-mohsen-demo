## 0. Non-negotiables

1. **All work lands in committed steps.** No task is finished while it has
   uncommitted changes. Split work into small, logical commits and commit each
   one as you go — see §2.
2. **Never commit secrets, patient data or generated artifacts.** `.env`,
   `app/uploads/`, `node_modules/`, `.next/`, `*.tsbuildinfo` are ignored and
   must stay ignored.
3. **Arabic is the default language** (`ar`, RTL). English is a secondary
   locale. Never ship English-only copy in the storefront.
4. **No prices anywhere.** Cost is discussed after the case is reviewed. This is
   a client policy, not a placeholder — see `design.md` §1 and §10.
5. **Read the Next.js 16 docs before writing Next code.** This is not the
   Next.js in your training data. Guides live in
   `app/node_modules/next/dist/docs/`. `app/AGENTS.md` explains why.
6. **Patient data is sensitive.** Treat names, phones, complaints, lab results
   and scans as confidential medical data (§9).
7. **Do not modify the supplied originals** in the repo root (`1.jpg`, `5.jpg`,
   the logo PNG, `color-palette.txt`, `font.txt`). They are source material.
8. **Report, don't guess.** If something is ambiguous, ask. If you find a bug
   that is outside the requested change, mention it; don't silently fix
   unrelated files.

## 2. Work must be committed in steps

This is the hard rule of this repository, not a suggestion.

### 2.1 Plan in units

Before editing, write down the units of work. A unit is the smallest change that
still makes sense on its own and leaves the tree working. Examples:

- "add the doctor filter to the directory" — one unit
- "fix the RTL arrow direction" — one unit
- "document the repo" — one unit (two files, same purpose)

If a request naturally contains three units, produce three commits — not one
large commit at the end.

### 2.2 Commit each unit immediately

- Commit after the unit is verified, before starting the next one.
- Never leave a working tree with uncommitted edited files at the end of a task.
- Never stack unrelated changes into one commit "because it is faster".

### 2.3 Verify before committing

Run the checks that apply to the change, from `app/`:

```bash
npm run lint                # ESLint (eslint-config-next)
npx tsc --noEmit            # type check
npm run build               # full production build (runs prisma generate first)
```

For UI changes, also run `npm run dev` and exercise the flow in both `ar` and
`en`. For data changes, run `npm run db:push` against the local database and
verify the affected admin screen.

If verification fails and the fix is outside the requested scope: stop, report,
and either revert the change or commit only the part that passes. Say which.

### 2.4 Staging rules

```bash
git add AGENTS.md CLAUDE.md         # explicit paths only
git status --short                  # review what is staged
git commit -m "docs: add repository operating guide"
```

- **Never** `git add .`, `git add -A` or `git add --all`.
- **Never** `git commit -a`.
- Check `git status --short` before every commit. Anything unexpected stays out.
- `DemoDrHoda` is a nested repository tracked as a gitlink. Its working tree
  already shows as modified (` m DemoDrHoda`) and that predates documentation
  work. Leave it alone; do not commit the gitlink.

### 2.5 Commit messages

The history uses `scope: lowercase imperative summary`:

```
app: build the six-step booking engine and team-request sheet
app: fix production build (static-safe root layout, schemas out of route files)
prototype: open the navigation drawer from a hamburger at every breakpoint
initial
```

- Scopes in use: `app:` (Next.js product), `prototype:` (root static HTML),
  plus `docs:` and `infra:` for their own work.
- One line, imperative, ≤ 72 characters, no trailing period.
- Body only when the *why* is not obvious; wrap at 72.
- Do not amend, rebase or force-push commits you did not create.

### 2.6 End-of-task checklist

- [ ] Every unit is its own commit with a message in the house style.
- [ ] `git status --short` shows nothing you created.
- [ ] Lint, type check and build pass (or the failure is explained).
- [ ] Docs updated when structure, commands or conventions changed.
- [ ] No secrets, uploads, build output or tool artifacts staged.

## 8. Architecture notes

### Routing and locales

- `src/proxy.ts` (Next 16's middleware file name) runs on the Edge runtime.
  It performs three jobs, in order: reject cross-origin mutations (403), gate
  `/admin` on the *presence* of a session cookie, then delegate everything else
  to next-intl.
- The proxy is deliberately optimistic — it cannot read Prisma. Real
  authorisation is `requireAdmin()` in `(admin)/layout.tsx` and
  `getCurrentUser()` in route handlers.
- `x-pathname` is forwarded on request headers so server layouts can identify
  `/admin/login`.
- URLs are `/{locale}/…`; `defaultLocale` is `ar`. `localePrefix: "always"`.
- `dir`/`lang` live on the `.m-site` wrapper, not `<html>`, so the admin
  dashboard and Next error pages keep their own direction.

### Data flow

- Storefront pages are server components that query Prisma directly
  (`(site)/[locale]/page.tsx` is `force-dynamic`).
- Mutations go through route handlers with zod validation
  (`lib/auth/validation.ts`, `lib/admin-schemas.ts`).
- Admin pages are client components under an authenticated server layout; they
  fetch `/api/admin/*` and use `sonner` for feedback.
- `getSettings()` is cached and is the only place settings are read.

### Auth

- Session token: 32 random bytes, stored in cookie `dm_session` (httpOnly,
  `SameSite=Lax`, `secure` in production, 30-day TTL, extended once past
  half-life). The database stores **only the SHA-256 digest** as `Session.id`,
  so a DB leak cannot be replayed.
- `lib/auth/index.ts` is the single place identity is resolved:
  `getCurrentUser`, `requireAuth`, `requireAdmin`, `login`, `logout`,
  `rotateSession`. Do not bypass it.
- Passwords are bcrypt-hashed; a dummy verification equalises timing for
  unknown accounts.
- Rate limiting is in-memory fixed-window (`lib/auth/rate-limit.ts`). It is
  per-instance by design; move it to Postgres/Redis before scaling horizontally.
- The proxy rejects cross-site non-GET requests by comparing `Origin` host to
  `Host`.

### Media pipeline

- Images: validated by magic bytes → `sharp` → WebP, quality ladder, dimension
  fallbacks, per-purpose ceilings (`lib/media/shared.ts`).
- Documents: PDF only, header-sniffed, ≤ 20 MB, stored byte-exact — a report is
  a legal record and is never re-encoded.
- **SVG is rejected on purpose**: it can carry script and would become stored
  XSS when served from the app origin.
- Each file gets a `Media` row; booking/team-request uploads are join rows that
  keep files out of the cleanup sweep.
- `instrumentation.ts` starts the cleanup schedule on boot; the same pass is
  exposed at `/api/cron/media-cleanup` for external schedulers. It sweeps stale
  PENDING rows, unreferenced files, untracked files and temp files.
- Files are served from `/api/uploads/[filename]`, never from `public/`.

### Email

`lib/email.ts` is fail-soft: no email failure may fail a booking. HTML parts are
escaped at the call site (`escapeHtml` in the bookings route).

## 9. Security, privacy and clinical rules

- **Patient data is confidential.** Do not log names, phones, complaints,
  filenames or document contents. `logError`/`logInfo` should receive
  identifiers, not payloads.
- **Never weaken auth.** No new public route may read patient data. Admin routes
  call `requireAdmin()`; public routes rate-limit.
- **Validate at the boundary.** Every route handler parses input with zod and
  returns `{ error, field? }` on 400.
- **No new remote hosts** in `next.config.ts` without a documented reason.
- **No `dangerouslySetInnerHTML`** on user or admin content. Blog bodies, if
  rendered, must be sanitised first.
- **No secrets in code, commits, fixtures or docs.** Use `.env`/Settings.
- **Do not weaken the upload pipeline**: no SVG, no mime-type trust, no
  skip-validation flags, no "temporarily disable cleanup".
- **Consent is required**: booking and team-request submissions must keep
  `consent: true` enforced server-side.
- This is a medical site. Nothing may imply a guaranteed result, a price, or a
  testimonial that has not been approved (`design.md` §10).

## 10. Design and content conventions

Read `design.md` before any UI work. The short version:

- **Colours**: only `--blue #20438E` and `--teal #007D77` (plus their derived
  tints/shades and the semantic states). WhatsApp green `#25D366` is the single
  sanctioned exception, for the WhatsApp mark only.
- **Signature device**: the 118° blue→teal diagonal. The two-door split is a
  straight 50/50 seam by exception.
- **Type**: Lama Sans, self-hosted, one family for Arabic + Latin. Display
  weights 300–500; 700–800 only for numbers, badges and short labels. No
  italics. No letter-spacing in Arabic.
- **Radii**: 2px buttons/inputs, 10px cards, 20px media, 999px pills.
- **Borders over shadows**; one soft elevation only.
- **Icons**: Phosphor on the storefront, lucide in the admin. Icons always pair
  with a label; no emoji in production UI.
- **Motion**: GSAP + ScrollTrigger on the prototype only; the Next storefront
  uses CSS/`site-behavior.tsx`. Everything collapses under
  `prefers-reduced-motion`.
- **Focus**: `:focus-visible` outline 2px teal, offset 3px. Never remove it.
- **Copy**: Arabic-first Egyptian voice, plain and safety-first, never salesy.
  Every visible string is bilingual; use `<Bi en="…" ar="…"/>` or the
  `messages/*.json` files. Placeholder data must stay flagged as
  «بيانات توضيحية».
- **Never publish prices.** Cost is discussed after the case is reviewed.

## 11. Verification playbook

Because there is no automated test suite, a change is verified by evidence:

1. `npm run lint` — no new warnings/errors.
2. `npx tsc --noEmit` — clean.
3. `npm run build` — succeeds.
4. Manual flows:
   - Storefront `/ar` and `/en`: layout direction, no overflow, fonts load.
   - Booking: 6 steps → submit → row in `/admin/bookings` → files served.
   - Team request: sheet → submit → row in `/admin/team-requests`.
   - Contact + newsletter: submit → rows in admin.
   - Admin: log out → `/admin` redirects to `/admin/login`; log in → dashboard;
     each edited CRUD screen persists.
   - Uploads: oversize file rejected, PDF accepted, a renamed `.exe` rejected.
5. RTL/LTR smoke test at 360 px, 768 px, 1440 px.

State in the commit body or final report what you actually ran. Never claim a
check you did not run.

## 12. Known gaps and gotchas

These are real and verified — fix them deliberately, in their own commits, not
incidentally:

- `package.json` → `seed:prod` runs `scripts/seed-production.mjs`, but
  `app/scripts/` does not exist. `npm run start:prod` will fail at that step.
- `src/instrumentation.ts` mentions `vercel.json`; that file is not present.
  The in-process scheduler is the only active path.
- `(site)/[locale]/layout.tsx` imports `./landing.css` twice (lines 12–13).
  Harmless, but redundant.
- `DemoDrHoda` is tracked as a gitlink and its working tree is already dirty.
  Do not stage or "clean" it.
- The commit `ad86db2` ("publish from-EGP-20,000 pricing…") contradicts the
  no-prices policy. Treat the current landing copy as authoritative and confirm
  with the client before republishing any price.
- Rate limiting is per process; do not rely on it across replicas.
- `Proxy` is the Next 16 name for middleware. Do not rename it back to
  `middleware.ts` without checking the installed docs.
- `prisma db push` is used instead of migrations. There is no `prisma/migrations`
  directory; do not invent one without discussing the deployment story.

## 13. Agent behaviour

- **Read first.** Inspect the relevant files and the Next 16 docs before editing.
  Prefer `rg` over guessing.
- **Match the surrounding code.** Naming, comment density, error shape,
  `@/` imports, bilingual prop pairs. The existing files are heavily commented
  with the *reasoning*, not the mechanics — keep that style.
- **Small diffs.** Do not reformat files you are not changing, do not reorder
  imports project-wide, do not rename things "for clarity" unless asked.
- **Comments explain why.** One clear sentence beats a block of restatement.
- **Never delete user work.** Unfamiliar files, uncommitted changes and the
  `DemoDrHoda` tree are presumed intentional — investigate before touching.
- **No destructive commands** (`git reset --hard`, `git clean`, `db push
  --force-reset`, dropping tables) without explicit confirmation.
- **Keep docs current.** If you change structure, commands, env vars or
  conventions, update `AGENTS.md` and `CLAUDE.md` in the same task (its own
  `docs:` commit) and bump the "Last verified" date.
- **Finish with a summary**: what changed, which commits you made, what you ran
  to verify, and what you did not verify.
